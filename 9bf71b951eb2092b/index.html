Ditech Booking API

Seven public endpoints — three reads, three writes, and one lookup — plus everything needed to test a photo upload end to end. Sourced from API-Requirements.md, which remains the canonical doc; this page is a rendered, hostable copy of it for quick reference. Last synced 2026-09-07.

Three legacy routes carry a /v1/ prefix (/v1/bookings, /v1/customers, /v1/services/{id}/availability/search) and are being retired (#69). Everything on this page is the newer, no-prefix surface that replaces them.

The public key above is not a secret. The admin key (/clarific/prod/api/keys/admin) is the opposite — a real credential. It must never appear in a shared doc, a repo, or any VITE_*/ NEXT_PUBLIC_* env var.

Reads

GET /services

Returns the tenant's bookable services. Session capacity and duration are config, not derived.

GET /service-area/check

Query params suburb and postcode. Confirms whether Ditech currently services that address.

GET /schedule/availability

Returns open slots for a given service and date range.

Writes

Two endpoints create work or an upload token; a third creates a request; a fourth looks one up.

POST /jobs

Creates a job directly (in-area, non-urgent path). Never send endsAt, resourceId or status — the server derives them. serviceId is optional.

{
  "serviceId": "…",          // optional
  "startsAt": "2026-09-10T09:00:00+10:00",
  "customer": { "name": "…", "email": "…", "phone": "…" },
  "notes": "…",
  "uploadToken": "…"          // optional — see POST /attachments/presign
}

POST /requests

Creates a request — out-of-area, urgent, reschedule or refund. Never auto-confirmed.

{
  "type": "…",
  "customer": { "name": "…", "email": "…", "phone": "…" },
  "relatedJobNo": "…",        // optional, for reschedule/refund
  "uploadToken": "…"          // optional — see POST /attachments/presign
}

POST /jobs/lookup

Job number plus a contact detail → job status. Rate limited separately from the other writes (see Looks like a bug, isn't).

POST /attachments/presign

Mints a short-lived S3 upload form. Same public key as every other route. Full flow: File uploads.

Request:
{
  "files": [
    { "filename": "leak.jpg", "contentType": "image/jpeg", "sizeBytes": 842104 }
  ],
  "uploadToken": null   // omit on the first call; pass one back to add more files to the same batch
}

Response · 201:
{
  "uploadToken": "…",
  "files": [
    { "attachmentId": "…", "url": "https://…s3…", "fields": { "…": "…" } }
  ]
}
Not covered by the write rate limit. Verified against the deployed WAF web ACL 2026-09-05: WriteRateLimit scope-matches /jobs and /requests exactly. Presign falls under the 600-per-5-minute general backstop instead, so uploading several photos before submitting the form never counts against the 30-per-5-minute write limit.

Looks like a bug, isn't

1. First request after ~15 minutes idle returns 502. Aurora Serverless v2 runs with MinCapacity: 0 and a 900-second auto-pause, so the cluster scales to zero and the first caller pays for the resume. Call it again and it succeeds. Tracked as #127 — this is a real go-live fault, not just a dev annoyance, because GET /services is the booking page's first call.
2. There is no /v1/ prefix on these seven routes. GET /v1/services is a plain 404 — a likely first wrong turn when porting old code.
3. Writes are rate limited — but not all of them the same way. The WAF WriteRateLimit rule matches POST /jobs and POST /requests exactly — nothing else. POST /jobs/lookup has its own separate limit (20 per 5 minutes). POST /attachments/presign isn't covered by either — it falls under the general 600-per-5-minute backstop, so a four-photo booking costs one write against the limit, not five. A burst of retries against /jobs or /requests from one browser can still trip WriteRateLimit well before any real customer would — wait 5 minutes.
Every booking created here is real. There is no test environment and no cleanup path — each one permanently consumes availability in production.

File uploads — full flow

Attaching a photo to a job or request never touches AWS directly from the browser. It's a three-step round trip: presign → upload straight to S3 → claim on submit.

Why there are no S3 credentials

Deliberate, not an oversight. An AWS key cannot be scoped to a single upload, cannot enforce a size or type limit, cannot be revoked for one person, and would grant read access to every tenant's files. The presigned form is the credential — single-file, single-use, short-lived.

The two hostnames

The bucket name isn't a secret — it appears in every presign response — and it blocks all public access (an anonymous GET of a stored object returns 403, verified).

Limits — booking page

Value
Files per presign call4
Max size per file10 MB
Accepted content typesimage/jpeg, image/png, image/heic, image/webp
Upload form validity15 minutes
  • HEIC is accepted on purpose — it's the iPhone camera default. Browsers generally can't render a HEIC thumbnail; show a filename/icon placeholder instead of assuming <img> works.
  • Content types match exactly, never by prefix — image/svg+xml is refused.
sizeBytes in the request is advisory, not a per-request cap. Verified live: the signed form always carries the fixed 10 MB ceiling, never the number you declared — declare 1 KB, upload 5 MB, and it succeeds. Validate file.size client-side; don't rely on having declared a small number.

CORS

Allowed origins on the bucket: http://localhost:5173 (Vite), http://localhost:3000, and the deployed site https://d245tm623nz562.cloudfront.net. An unlisted origin gets a 403 with no CORS header — in a browser that surfaces as an opaque network failure rather than a readable error. If uploads fail only in the browser but work from curl, check the origin first.

Runnable test — presign, upload, verify

BASE=https://d10x73j3qxkfam.cloudfront.net
KEY=tenant_ditech_pub_3affa5c7-fc84-4332-a9dd-707076af0eb3

# 1. ask permission (one call covers the whole batch, max 4)
curl -s -X POST "$BASE/attachments/presign" \
  -H "X-API-Key: $KEY" -H 'Content-Type: application/json' \
  -d '{"files":[{"filename":"test.jpg","contentType":"image/jpeg","sizeBytes":12345}]}' > presign.json

# 2. upload straight to S3 — every returned field, then the file LAST
URL=$(jq -r '.files[0].url' presign.json)
ARGS=(); while IFS=$'\t' read -r k v; do ARGS+=(-F "$k=$v"); done \
  < <(jq -r '.files[0].fields | to_entries[] | [.key,.value] | @tsv' presign.json)
curl -s -o /dev/null -w '%{http_code}\n' -X POST "$URL" "${ARGS[@]}" -F "file=@test.jpg"
# expect: 204

# 3. attach to a booking — pass the token on your normal submit
TOKEN=$(jq -r .uploadToken presign.json)
# ... POST /requests or /jobs with  "uploadToken": "$TOKEN"  in the body

Success is 204 No Content, not 200, and the body is empty.

file must be appended last. S3 stops reading at the file part, so anything added after it is never seen — and the failure is a signature error that never mentions ordering. This is the most common way to get this wrong.
Don't set a Content-Type header on the upload request — let the browser set the multipart boundary; the file's own content type is already inside the returned fields.
Treat fields as opaque — append every key exactly as returned, don't rename, reorder or add. The real set includes Content-Type, key, bucket, Policy, X-Amz-Algorithm, X-Amz-Credential, X-Amz-Date, X-Amz-Security-Token, X-Amz-Signature — note the capitalised Policy and X-Amz-*, and that the exact set varies with how AWS signs.

What happens after you submit the booking

Passing uploadToken on POST /requests or POST /jobs attaches the photos. Behind the scenes the file is copied to a permanent location and the record repointed at it — verified live 2026-09-05: staging/ditech/{token}/{id}.jpeg becomes tenants/ditech/requests/ditech-rq-5/{id}.jpeg. Nothing is re-uploaded and the UI never handles the permanent key.

A bad token never fails a booking. An unknown or expired uploadToken is logged and ignored, and the booking still succeeds — deliberate, so a customer never loses a booking because a photo expired. A 201 from POST /requests is not evidence the photos attached.
Anything never attached to a booking is deleted after 24 hours. That's the staging cleanup working as intended, not a fault. Attached photos are permanent.
